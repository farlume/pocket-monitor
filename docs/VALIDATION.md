### Bulk 停流候选修复（2026-09-27）

- 用户提交的报告确认使用 `0.1.4-uvc-diagnostic`，手机 OPPO PLG110、Android 16 / SDK 36，USB VID/PID `2b89:5348`。报告列出 MJPEG/YUY2 模式，其中 1080p MJPEG 为 60/120/240 fps，没有 1080p30；能力声明不等于实际可持续采集。
- 报告显示 epoch 24 的 720p60 MJPEG 启动返回约 110 ms 后收到首帧；切到 1280×1024/60 后，关闭、打开和协商均返回，但 8 秒无帧。回退到 720p60 仍无帧。结合用户反馈，这说明只重建相机尚未解决必须拔插的问题，不能将 Java 启动返回解释为 native 传输已成功。
- 新候选包 `0.1.4-uvc-bulk-stop` 在原生相机销毁后，通过 `USBDEVFS_CLEAR_HALT` 清理视频流 Bulk IN 端点，再重新协商；断开清理也执行该步骤。仅操作 VideoStreaming 接口的 Bulk 输入端点，不强制抢占接口。使用 ioctl 同步重置设备 halt 和主机端点数据切换状态，诊断记录端点、返回码和接口申请/释放失败。
- 依据是 [Linux UVC 驱动的 Bulk 停流流程](https://github.com/torvalds/linux/blob/v6.6/drivers/media/usb/uvc/uvc_video.c#L2106)；这仍是候选原因。现有报告没有端点描述符，尚未确认该卡是否走 Bulk，也未验证新包能否恢复。ISO 端点不执行此清理；不发 USB 总线重置，也不增加自动重试次数。
- 新增自有 JNI helper，固定 NDK 28.2.13676358，第三方 UVC 依赖版本不变。两次系统弹窗的实际内容及此前授权时序改动效果仍待用户确认。
- 本轮实际执行：52 项 Android 测试通过，无失败、错误或跳过；其中新增 6 项覆盖端点筛选/去重、接口申请失败、ioctl 失败、异常释放、ISO 跳过及释放失败诊断，切换测试检查销毁 → Bulk 停流 → 重建顺序。Debug APK 构建通过，Lint 为 0 错误、18 警告；项目文档及 136 个翻译键检查、10 项 Python 测试和差异空白检查通过。共享 JVM 测试未重跑。
- APK 内四种 ABI 的新增 JNI 库均检查了导出符号及 16 KB ELF 段对齐，APK 的 ZIP 对齐检查通过；这些检查不执行真实 USB ioctl，也不证明采集卡切换成功。
- 后续用户反馈：仍只有原分辨率能出画，切到更高格式后自动降级失败，手动切回也无法恢复，必须再次拔插。此次反馈未附新的版本号与 `Bulk stop` 返回值，端点清理的实际执行情况尚待诊断文本确认；不能将上一候选修复标为通过，也不能据此认定该卡只支持 720p。下一步收集失败后的完整连接诊断，区分清理未执行、返回失败和执行成功但无效，再定位 native 启动/传输问题。

2. 首次连接拒绝相机权限，再允许；拒绝 USB 权限，再连接。不可崩溃或重复弹窗。
3. Mac 输出 1080p60，手机以默认 720p30 开始采集；必须实际看到 Mac 桌面和移动窗口。
4. 如设备报告 1080p30 / 1080p60，在设置中逐个验证；标称能力不等于手机最终能稳定运行的能力。
5. 横竖屏、全屏退出、旋转和双指缩放：画面不应被拉伸。
6. 拔插采集卡、切换到后台再回来、锁屏再解锁，重复至少 5 次；检查连接恢复、资源释放与供电。
7. HDMI 拔出时观察卡输出黑屏/彩条还是停止发帧，确认 App 提示与实际传输状态相符。
8. 持续预览 15 分钟，记录卡/手机发热和帧率。观察重连后是否出现设备忙。
9. 手动选择不同格式，出画至少 3 秒，彻底关闭再打开 App；确认恢复该格式。更换不同 VID/PID 的卡，不应套用原卡的设置。
10. 用能复现启动无帧的卡/模式验证：8 秒后尝试降级，最多两次；拒绝权限、拔出、切后台应取消旧尝试。卡自行输出黑屏/彩条仍属于有视频帧，不会触发无帧降级。
11. 预览中反复切换三个标签、明暗模式、配色和语言；检查实际视频无异常中断。关闭亮屏开关后确认屏幕遵循系统超时；切换帧率显示并重启验证偏好保存。
12. 观察首帧到达时等待提示是否及时消失，避免额外等待一次每秒状态刷新。此处不等于实际 HDMI 采集延迟已测量或降低。
